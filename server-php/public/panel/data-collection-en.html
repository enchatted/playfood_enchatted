PLAYFOOD — data collection

Purpose and identifiers

When statistics are enabled, PLAYFOOD records game activity for project KPIs such as visits, recorded browser profiles, mission attempts, completion and time spent. The random learner_id is saved in browser local storage as playfood-learner. It identifies a browser profile, not a verified child. Shared browsers can share an ID; clearing storage or changing browser/site can create another. Without working storage it lasts only for the page load. This is a persistent pseudonymous identifier, not a guarantee of complete anonymity. A new random session_id identifies a page visit; a random attempt_id identifies a game attempt.

Fields stored

Each event has ts (server arrival time in epoch milliseconds), learner_id, session_id, type, island, game, score, stars, duration_s, progress, language and returning. Game-attempt events may also have attempt_id and passed (pass/fail on a finished round). Fields that do not apply are empty. Event types are session_start, hero_chosen, island_enter, game_start, game_finish, game_abandon, session_end and phygital_redeem. For hero_chosen, the game column contains the selected predefined hero ID; it is not a game name. For phygital_redeem (a code for an offline activity was accepted), the game column contains the activity ID from the school's activity list; the typed code itself is not stored. progress is recorded objective progress on exit, not a learning score. language is the game language, not country; returning means an existing browser statistics ID was found.

Time measurements

Ended or abandoned rounds may include timing_version=1 and six non-overlapping totals in seconds: active_s (available play with recent input), learning_s (guidance/help/decision cards displayed), paused_s (pause or exit menus), hidden_s (hidden or unfocused page), idle_s (time after five minutes without input during play or guidance), other_s (loading, transitions and results). Guidance time is not proof of reading; active time is not proof of learning. The duration_s field is elapsed round or visit time and includes pauses and hidden time. Missing final events leave duration unknown; older records may lack time splits. No individual keys, pointer movements or answers are saved in the statistics database.

Data outside the event rows

The event allowlist excludes names, email addresses, IP addresses, user-agent strings and free text. This PHP backend does not store IP addresses or user-agent strings, including hashed addresses. Request limits use installation-wide counters in SQLite: 5,000 event requests, 1,200 activity-code redemptions and 30 login attempts per minute. An event cap defaults to 200,000 accepted event rows per day. Aggregate diagnostic counters track accepted requests and rejection categories, without network identifiers. The hosting provider may keep separate access or error logs; the operator must check those settings.

Setup provisions one staff account. Its email and password hash are stored in the private installation.json file. Staff login sessions are stored as token hashes, email and expiry in SQLite. The browser keeps the current panel token in session storage; panel inactivity expires the session after 30 minutes. The browser also keeps game progress separately from statistics. A saved Play Code restores progress and does not link statistics IDs across browsers. Activity-code validation uses the private phygital-codes.json file; redeemed activity IDs stay with the saved game progress.

Storage and access

This PHP installation stores playfood.db (SQLite), installation.json and the activity-code configuration in a playfood-private-... directory outside the public website root. Signed-in panel staff can view summaries, export event rows as CSV and obtain a database backup through the authenticated API. A database backup also contains staff session records and diagnostic counters, so keep it private. CSV retains ts and adds local_time in the school timezone and timestamp_utc in ISO 8601 UTC. Export filters use the school timezone. The operator must confirm the hosting provider, country, access and any server logs before use. This note does not certify a hosting location.

Defaults, retention and switching off

Statistics and panel access are disabled unless enabled at setup. The private installation.json file holds the boolean enabled setting, timezone and retention_months (24 by default). On the first API request of each calendar day in the school timezone, records older than the configured month cutoff are purged. An idle site waits for a request; there is no scheduled background purge. Maintenance also runs when collection is disabled. Already exported CSV, PDF and backups are separate files and are not automatically purged.

To switch off, set enabled to false in the private installation.json and save valid JSON. The change applies on the next API request: new events are discarded and panel data access is disabled. Reload the game page so the browser also reads the changed setting. Set enabled to true to enable it again, then select Check again in the panel. Activity-code redemption remains available while statistics are off. Switching off does not erase old database rows or clear browser IDs/progress. The installation operator manages existing copies and retention requests. Updates must preserve the private directory and its existing settings, accounts, activity codes and database.
